# Dedicated worker VM

Issue jobs execute in a Linux VM with no Mac directory mounts. The trusted worker account keeps the scoped worker token and GitHub delivery credential in its private home. Provider CLIs and the threat-model verifier run as a separate `blueprint-agent` account. Issue worktrees are the only shared writable data. Configured checks run in the VM's own rootless Docker daemon with the current worktree mounted read-only, no network, and no extra privileges.

The worker refuses to claim jobs from a Mac process or an ordinary container. It verifies that it is in a VM, that host directory mount types are absent, and that it can switch to the separate agent account. These checks complement the plain-mode VM configuration in [`deploy/worker-vm/lima.yaml`](../deploy/worker-vm/lima.yaml).

## Local Mac staging setup

1. Install Lima, then create the worker with `limactl start --name blueprint-gate-worker deploy/worker-vm/lima.yaml`. Lima's Docker template provisions a rootless daemon inside the guest. Do not mount the Mac home, repository checkout, SSH agent, or Docker socket into the guest. The checked-in bootstrap checks the guest boundary and daemon before installing the worker.
2. Clone Blueprint Gate inside the VM, then run `scripts/bootstrap-worker-vm.sh` there. It installs the Python worker and Codex CLI, creates the agent account, clones the base repositories, builds a locally pinned check image, and writes a private `worker.yaml`. A private Threat-Models checkout needs repository-scoped GitHub authentication in the VM or a credential-free copy of that checkout from the Mac; rerun bootstrap after it is available. Keep the base checkouts under `/srv/blueprint-gate/repos` and the worktrees under `/srv/blueprint-gate/worktrees` so Git's absolute worktree metadata remains valid.
3. Provision the issued scoped worker credential as `~/.config/blueprint-gate/staging-worker.json` in the VM with mode `0600`. Its `worker_id` must match `worker.yaml`. Do not copy the Mac's broad GitHub login or administrator token. Authenticate `gh` under the trusted VM worker account with a repository-scoped delivery credential and run `gh auth setup-git`. Authenticate Codex under `blueprint-agent` with its own provider account. Provider credentials stay under `/home/blueprint-agent`; GitHub and worker credentials stay in the supervisor's mode `0700` home.
4. Start the control services on the Mac with `./scripts/start.sh --control-only`. In a separate Mac terminal, forward the guest's loopback port through SSH: `ssh -F "$HOME/.lima/blueprint-gate-worker/ssh.config" -o ExitOnForwardFailure=yes -N -R 127.0.0.1:8000:127.0.0.1:8000 lima-blueprint-gate-worker`. From the VM, `curl http://127.0.0.1:8000/health` must succeed. This tunnel exposes the control API only on the guest loopback interface and preserves the existing local-only HTTP rule.
5. Run `scripts/verify-worker-vm.sh` inside the VM. It tries to read a supervisor-only sentinel as the agent, writes a normal workspace result, and runs a read-only networkless check container. Then run `scripts/run-worker-vm.sh --once` to verify the paused worker can authenticate and claim no work. After provider and GitHub logins and repository policy are ready, resume dispatch intentionally and start `scripts/run-worker-vm.sh` in the VM foreground. Keep the same VM, worker ID, checkouts, and worktree paths across restarts to preserve claim affinity and interrupted work.

## Staging evidence and limits

On 18 October 2026, local staging used a plain-mode Lima VM on this Mac with no host directory mounts and its own rootless Docker daemon. The agent could write a normal fixture worktree but could not read the supervisor's private credential directory or modify protected Git metadata. A malicious check fixture could not see that credential path or reach a network address; a normal check read the active fixture and passed. `scripts/run-worker-vm.sh --once` reached the paused control plane using the scoped worker credential. The repository test suite passed on the Mac.

The VM does not yet have provider subscription or repository-scoped GitHub delivery authentication. No real issue job, verifier/PR delivery sequence, or pause/restart recovery has completed inside it. Provider outbound access is not yet limited to approved endpoints; only configured checks have network disabled. The two threat-model controls remain **not in place** until a real ticket passes end to end and outbound policy is verified. The VM is local staging evidence, not a claim of production deployment.
